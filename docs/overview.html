Overview

A software factory for coding agents

PranavSkills is a small, opinionated toolkit that turns a coding agent from a fast guesser into a disciplined engineer. It is a set of composable skills (short procedures the agent loads only when a trigger fires) arranged on one workflow spine, rendered from a single source into Claude Code, Codex, and Kiro. The bet is simple. The model matters less than the environment around it. Give the agent a clear task, legible code, short feedback loops, verification it cannot fake, and controls it cannot silently rewrite, and it produces work you can actually maintain.

What you get

25 focused skills on a plan-first spine, a JIT architecture knowledge base, and a linter that keeps the whole thing honest.

Who it is for

Anyone keeping real software alive with agents, where a misunderstanding is expensive and code has to stay changeable for months.

The one idea

Front-load the thinking, verify from a vantage the author did not write, and keep a human on every irreversible step.

The problem it solves

Coding agents are excellent at one-off changes and getting a test to pass. They are not good at keeping a codebase easy to change over time. The reason is structural. Models are trained to make tests go green in seconds, and there is no fast signal for "will this still be easy to edit in three months," so nothing rewards good design. Left unsupervised, an agent quietly wraps everything in try and catch, casts away the type system, and scatters one idea across eleven files. The bill arrives later, as an incident nobody can trace back to the decision that caused it.

The tempting fix is to remove the human and pour effort into more automated review. That raises the floor. It catches the dumb stuff. It does not move the ceiling, because a reviewer can only flag patterns it already knows, and the hardest maintainability calls depend on where the system is going, which is not a pattern.

So this toolkit does the opposite of a lights-off factory. It puts the thinking up front (where a bad decision is cheap to change), makes verification independent (so a green means something), and keeps a person on merge, deploy, taste, and anything irreversible. You move a few times faster, safely, instead of ten times faster into a wall.

The spine

Every non-trivial change walks the same path. Each stage has one job and hands a concrete artifact to the next, so work survives a fresh context or a handoff to another agent or person.

triage → grilling → spec → to-tickets → implement (+ tdd, + verify, + browser) → code-review → human QA │ │ │ │ │ gate resolve decide split into review from reversible the open every independently a fresh vs not questions decision reviewable slices context

orchestrate moves one project through that sequence and stops at every context boundary. supervise coordinates several project orchestrators at once through cmux, while each project keeps its own tickets, worktrees, tests, and review boundary. The spine is a default, not a ceremony. A typo skips straight to the fix. A data migration earns the whole path.

Why a spine and not one big prompt. Planning up front is what makes parallel and unattended work correct. A decision-complete spec plus independently reviewable slices means a different agent, or a person, can pick up any piece without a shared memory of the conversation. That is the thing a monolithic "just build it" prompt cannot give you.

Each skill is a short procedure with a trigger. The agent loads one only when the moment calls for it, which keeps the always-on context small. They compose freely.

How to use it

You do not memorize the skills. You describe the work and the right skill fires on its trigger. These are the common shapes.

SituationPath
A small, clear changetriage → implement → verify
An unknown buginvestigate → tdd → verify → code-review
A new featuregrilling → spec → to-tickets → orchestrate
A greenfield projectgrilling → spec → agent-arch → to-tickets → orchestrate
A scoped fix that ships on its owntriage → change-contract → implement → verify → commit
Reviewing someone else's changediff-review (read-only, refute the claims, report blockers)
After an incident is understoodinvestigate → postmortem
Stopping mid-task, or resuminghandoff (write on stop, read first on resume)
Several projects at oncesupervise → cmux → one orchestrate per project

The rule of thumb. If a misunderstanding would be expensive, spend the minutes up front. If it would not, just do the change and verify it.

The principles

Process before prompting

Resolve ambiguity before implementation. The cheapest place to change your mind is a design doc, not a 2000-line diff.

One vertical slice at a time

Each ticket crosses the layers needed for one observable behavior and fits in one useful context window. No half-built horizontal layers.

Verification must be independent

A signal the implementer authored proves only that the author agreed with themselves. For anything consequential, the expected value comes from a source the code cannot reach.

Fresh context for review

The author should not approve its own assumptions. Review runs in a new context against the spec and the standards.

A human owns the irreversible

Agents propose. Merge, deploy, data changes, and anything you cannot take back stay with a person or a gated system.

Mechanical guardrails beat prose

A type that makes a bad state unrepresentable, a lint, or a required check beats another paragraph that says "be careful." Encode the lesson at the strongest rung that holds.

Small skills beat a giant prompt

Load a procedure only when its trigger fires, so the always-on context stays small and legible.

Say what you know, and how you know it

Grade a claim by where its evidence lands, from "I said so" up to "I ran it and reproduced it," and state the rung out loud.

The through-line. Every automated reviewer catches the patterns it already knows. The way to keep quality high is a ratchet, not a pile. When review catches a recurring mistake, promote it to the strongest guardrail that will hold (a type, a lint, a canonical helper) so it can never reappear, and move the calls a reviewer cannot make to design time, where a human applies judgment cheaply.

How it is built

One source tree is the single source of truth. A renderer installs it into each harness by symlink, so an edit is live everywhere at once, and a linter enforces the conventions that keep the skills sharp.

PieceWhat it does
skills/core/The harness-neutral skills. One directory each, a short body with a trigger description.
skills/_shared/Reusable formats and templates (spec templates, the change contract, the tracker format).
knowledge/agent-arch/A just-in-time architecture and harness knowledge base, loaded per topic through an index, not all at once.
profiles/Per-harness targets and selections for Claude Code, Codex, and Kiro.
scripts/render.mjsInstalls a profile by symlink. It refuses to overwrite real directories and only retracts links it owns, so it never deletes your data.
scripts/doctor.mjsLints every skill. Four-key frontmatter, a 40-word ceiling on descriptions, triggers that fire, no harness names in shared bodies, a plain-writing check, and an aggregate context budget.

Descriptions are triggers, not summaries. Detail lives behind just-in-time links. A skill never names one harness in a shared body. Because the linter enforces these mechanically, the library stays legible as it grows.

Safety and authority

The workflow separates who can do what, so a mistake stays contained.

  • Implementation agents work in scoped branches or isolated worktrees.
  • Reviewers use a fresh context and never approve their own assumptions.
  • Merge, deploy, and production capability belong to a supervisor, CI, or a human.
  • Irreversible operations require explicit human ownership.
Local instructions and hooks are not security boundaries. They improve behavior. Real enforcement comes from least-privileged credentials, sandboxes, branch protection, required CI, and protected deployment environments. The toolkit is designed to sit inside those, not to replace them.

Get started

Requirements are Git and Node. The renderer generates a context file per harness, so preview first and back up any existing one.

git clone https://github.com/PranavG19/PranavSkills.git cd PranavSkills # see what each harness targets before touching your home directory cat profiles/codex.json # preview, render, then validate node scripts/render.mjs --dry-run node scripts/render.mjs node scripts/doctor.mjs

Then make it yours. Edit AGENTS.md to describe how you want an agent to work, edit or add skills under skills/core/, and re-render after changing which skills are selected. The full authoring rules live in CONVENTIONS.md.
